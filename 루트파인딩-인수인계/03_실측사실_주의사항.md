### 승인 루트가 5,407건이다
"사용자 50명 = 데이터도 작다"는 전제가 틀렸다.
전체 목록 로드·렌더는 불가능하다. 그래서 웹 개념도는 **검색해야 목록이 뜨고**,
검색 전에는 Firestore 조회조차 하지 않는다(읽기 0회).

### 화면상 "개념도"는 `concepts/` 컬렉션이 아니다
| 구분 | 실제 컬렉션 | 조건 |
|---|---|---|
| 리드 | `route_reports` | `status == 'approved'` (+ `typeRoot == '리드'`) |
| 볼더링 | `bouldering_reports` | `status == 'approved'` |

`concepts/{산}/routes`는 사실상 미사용이라 규칙에서도 제거했다.

문서 필드(실측): `routeName, overview, imageUrl, imageUrls[], typeRoot, zone, mountain,
avgDifficulty, difficulty, latitude, longitude, authorUid, equipment, pioneer, status, timestamp`
- 사진: `imageUrls[0]` → `imageUrl` → `pitches[].imageUrls[0]` 순으로 폴백
- 피치는 문서의 **배열 필드** `pitches[]` (서브컬렉션 `pitches`와 별개)

### 이미지 URL이 GCS 원본 주소다
`https://storage.googleapis.com/<bucket>/<path>` 형식으로 저장돼 있다.
이 형식은 Storage 보안 규칙이 아니라 **GCS IAM**을 타므로 그냥 쓰면 **403**.
→ 클라이언트에서 `getDownloadURL()`로 재변환해서 쓴다 (웹 `ConceptListView.vue` 참조).

### Firestore 리스너는 permission-denied 후 자동 재시도하지 않는다
규칙 배포 전에 `onSnapshot`이 걸리면 **죽은 채로 남는다.** 조용히 빈 목록이 된다.
→ 실패를 상태로 기록하고 "다시 불러오기" 버튼 + 저장 성공 시 재구독하도록 짜뒀다.

## 구현 규약 (앱 이식 시 반드시 맞출 것)

### 라인 그리기 — 좌표로 저장 + 합성본 동시 업로드
- 선/글자는 **0~1 정규화 좌표**로 저장 → 썸네일·전체화면 어디서든 정확히 겹친다
- 선 굵기 = 가로의 **0.6%**, 글자 = 세로의 **4%**, 글자 외곽선 = 글자크기의 **18%**
- 곡선은 점을 직선으로 잇지 말고 **이웃한 두 점의 중점을 지나는 2차 베지어**로
- 업로드 시 **원본 + 라인 합성본 두 장**을 올린다.
  승인되면 합성본이 개념도 `imageUrls`에 들어간다
  (목록·캐러셀·뷰어는 URL을 그냥 `<img>`로 띄우므로 원본을 넣으면 라인이 사라진다)
- **합성은 반드시 업로드 시점에.** Storage는 기본적으로 CORS 헤더를 주지 않아
  이미 올라간 이미지를 canvas로 다시 그리면 `toBlob()`이 SecurityError로 막힌다

### 지도 마커 앵커 (PNG 알파 실측값)
Google Maps Icon의 기본 anchor는 이미지 **하단 중앙**인데, 마커 PNG(200x200) 아래에
투명 여백이 있어 그냥 쓰면 핀이 위로 뜬다.

| 아이콘 | 핀 끝 비율 | 구멍(숫자 자리) 중심 비율 |
|---|---|---|
| `lead_marker.png` | 0.8300 | 0.4037 |
| `bouldering_marker.png` | 0.8450 | 0.4233 |

- 핀 anchor Y = `높이 × tipRatio`
- 숫자 라벨 anchor Y = `라벨크기/2 + 높이 × (tipRatio - holeRatio)`

### 그리기 UI 함정
`<img>` 위에서 드래그하면 브라우저 기본 이미지 드래그가 발동해 포인터 이벤트가 끊기고
선이 토막난다. `draggable="false"` + `dragstart` 차단 + `pointer-events:none` + `setPointerCapture`
네 겹을 다 해야 한다. (RN은 다른 방식이지만 같은 종류의 함정이 있을 수 있음)

## iOS 빌드

### gRPC 문제의 진짜 원인은 `use_modular_headers!` 였다
최초 에러("Swift pods cannot yet be integrated as static libraries")를 넘기려고 전역으로 켰는데,
gRPC-Core의 헤더 배치와 맞지 않아 `Pods/Headers/Private/grpc/gRPC-Core.modulemap not found`로 이어졌다.
패치를 한 겹 벗길 때마다 다음 불일치가 드러나는 "양파 까기"였다.

→ RNFB 공식 권장인 **static framework 링크**로 전환:
```ruby
$RNFirebaseAsStaticFramework = true
use_frameworks! :linkage => :static
```
그리고 gRPC용 `CLANG_ENABLE_EXPLICIT_MODULES = NO` 패치 제거.
이 방식으로 `pod install` 통과. **Xcode 빌드는 아직 미검증.**

### RNFB는 25.1.0. 26으로 올리지 말 것
- 25가 쓰는 firebase-ios-sdk 12.15.0은 **Xcode 26.2+ 를 요구** = 생태계가 정식 대응했다는 뜻
- **v26은 New Architecture가 필수**다. RN 0.76.9에서 켜는 건 큰 작업이라
  RN 업그레이드와 묶어서 별도로 진행해야 한다

## 코드 관리

### 제거한 화면은 파일을 지우지 않았다
게시판·크루·홈은 **라우팅만 끊었다**. 되살리려면 주석 복구.
- 앱: `navigation/MainNavigator.tsx`, `types.ts`의 주석 블록
- 웹: `router/index.js`의 주석 블록

앱 `navigation/types.ts`에 `PostDetail` 등 라우트 **타입은 남겨뒀다** —
보존한 화면 파일(`MyPostsTab` 등)이 참조해서 지우면 타입체크가 깨진다.

### 웹은 git 저장소가 아니다
`~/routefinding-web`에 git이 없다. 되돌릴 수단이 Hosting 롤백뿐.
`ConceptListView.vue.bak`은 그래서 남겨둔 원본 백업이다.
